# Stack pack: SvelteKit

Pack sections are appended by different pipelines; each owns its own heading.

## Security surfaces

The SvelteKit app is usually a thin client of a separate API; the API owns authorization, but the SSR layer can leak data, forward credentials, and open redirects. Read the hook and server files first.

- **hooks.server.** `handle` runs on every request: check it authenticates before resolving routes that need it, does not trust forwarded headers it did not validate, sets security headers, and does not attach secrets or the full user record to `event.locals` that later reach page data. Check `handleFetch` for credential or cookie forwarding to origins other than the API (a fetch to a user-influenced URL with the session attached is a leak). Check `handleError` does not return stack traces.
- **Load functions.** `+page.server.ts` and `+layout.server.ts` `load` return values are serialized into the HTML and visible to the browser. Anything returned (user objects with email or flags, tokens, internal ids, upstream error bodies) is public to that page's viewer. Check layouts: a `+layout.server` load runs for every child route, including public ones, and its data reaches all of them. Universal `+page.ts` loads run in the browser too, so they must not use server-only secrets.
- **Auth guards.** A guard in a layout `load` does not protect sibling `+server.ts` endpoints or form actions; each endpoint and action needs its own check. Redirect-based guards in `+page.ts` run client-side and are bypassable; authorization must be enforced at the API or in server files. Check that an unauthenticated load does not still fetch and return private data before redirecting.
- **Form actions and CSRF.** SvelteKit rejects cross-origin form POSTs by default (`csrf.checkOrigin`); look for it disabled, for `+server.ts` handlers that accept state-changing GET, and for mutations reachable through content types the check does not cover. Actions must validate input server-side and re-check authorization; hidden fields (ids, roles, prices) are caller-controlled.
- **Endpoints (`+server.ts`).** Treat as public API routes: authentication, input validation, SSRF in proxy or fetch-by-URL endpoints, open proxying of the upstream API with the user's token, permissive CORS headers.
- **Redirects.** `redirect()` or `goto()` with a target from a query parameter (`next`, `redirect`, `returnTo`, OAuth `state`) must be validated as a same-origin relative path; check `//host`, `/\host`, and scheme tricks. Check OAuth callbacks verify state and use fixed redirect URIs.
- **Cookies.** Session and refresh cookies: `httpOnly`, `secure`, `sameSite`, scoped `path` and `domain`, lifetime. Tokens stored in `localStorage` or readable cookies, tokens placed in URLs or in returned page data. Cookies set from `event.fetch` responses are not forwarded automatically; check any manual forwarding.
- **SSR data leakage across requests.** Module-level mutable state or singletons (stores, caches, API clients with a token) are shared between concurrent requests on the server; per-user data in them leaks between users. Svelte stores created at module scope and written during SSR have this problem; `event.locals` and context are per request.
- **{@html} and injection.** `{@html}` with any user-influenced or API-provided string is XSS unless sanitized with a maintained sanitizer at the boundary; check markdown renderers (raw HTML enabled), `innerHTML`, `eval`, `new Function`, `href`/`src` bound to user URLs (`javascript:` scheme), `<svelte:element>` with user tags, and JSON embedded into `<script>` (`</script>` breakout) in `app.html` or head injection.
- **Environment variables.** `$env/static/public` and `$env/dynamic/public` (the `PUBLIC_` prefix) ship to the browser: anything secret there is exposed. `$env/static/private` and `$env/dynamic/private` must only be imported from server code; SvelteKit blocks client imports at build time, but a private value copied into returned data or a public constant defeats it. Check `vite.config` `define` and `envPrefix` for exposing private values, committed `.env` files and secrets in build args.
- **Server-only modules.** Files under `$lib/server` or named `*.server.ts` must hold credentials and server logic; check they are not re-exported from client-importable barrels, and that secrets are not inlined in shared `$lib` code.
- **Rendering mode.** Routes with `ssr = false` and `prerender = true`: prerendered pages must not embed per-user or secret data at build time; client-only pages rely entirely on API authorization.
- **Third-party scripts and headers.** Analytics or embed scripts loaded without integrity or restriction, missing CSP (`kit.csp`), framing allowed on sensitive pages, `Referrer-Policy` leaking tokens in URLs. Also check `package.json` for new or unpinned dependencies and lifecycle scripts, and CI workflows that build with secrets.

Typical non-findings: `PUBLIC_` variables that are meant to be public (API base URL, public keys); client-side guards that are only UX when the API enforces authorization; a load function returning only fields the page renders to that same user.

## Debt conventions

Hunters and verifiers use this section as the house pattern to measure drift against. A pattern the repo's CLAUDE.md documents as intentional is not debt.

- Svelte 5 runes only: `$state`, `$derived`, `$effect`, `$props`. Legacy reactive statements (`$:`), `export let` props, stores used for local state, `on:` event directives, and `<slot>` where snippets are the house style are drift. `$effect` that only derives a value (should be `$derived`) or that sets state it reads (loop risk) is a smell.
- Data loading: initial data belongs in `load` functions (server or universal), not in `onMount` or effects, unless the page is client-only by design (`ssr = false`). Components that fetch what a parent `load` already has, or waterfalls of sequential awaits that could be parallel, are debt.
- TanStack Query: stable, centralized query keys; mutations invalidate the keys they affect (missing invalidation leaves stale lists, over-broad invalidation refetches everything); no copying query data into local state; consistent `enabled`, stale-time and error handling.
- Server/client module boundaries: secrets, server-only helpers and private env stay in `$lib/server` or `+server`/`+page.server` files; client code never imports them. Shared code that reads `window`/`document` at module top level breaks SSR.
- Generated API client: never edited by hand. Hand-written types that duplicate generated ones, or casts that bypass them (`as any`, non-null assertions on API data), are drift.
- Component size: components past a few hundred lines mixing data fetching, form state and markup; copy-pasted markup across routes that wants a shared component; prop drilling more than two levels instead of context or a snippet.
- Accessibility debt (mandatory where the house rules say so): interactive elements that are not buttons or links, missing labels, icon-only controls without an accessible name, focus not managed in dialogs and menus, color-only state, ignored `svelte-check` a11y warnings or `svelte-ignore` comments with no reason.
- Typing: `any`, `@ts-ignore`, `@ts-expect-error` without a reason, loosely typed event handlers; strict mode assumed.
- Tests: component tests asserting implementation details, snapshot sprawl, `waitFor` or fixed timeouts instead of awaiting the visible state, e2e specs sleeping.
- Dead-code oracles: file-based routes (`+page`, `+layout`, `+server`) are entry points by convention; components are dead only when no import, dynamic import or route references them; exports in barrel files need a whole-tree search including tests and stories; unused dependencies need a check of config files (vite, tailwind, svelte, eslint, postcss) before they are called unused.
